# 需求收拢、产品架构与规格生成

在 S0–S3 使用。本参考负责把自然语言需求转成可评审规格；生命周期状态与阶段门槛以 `lifecycle-orchestration.md` 为准，权威字段以 `project-snapshot.md` 为准。

## 1. 极低摩擦输入

- 接受一句话、会议记录、PRD、截图、Figma/页面链接或已有原型；先提取已知事实，不重复询问。
- 首轮优先补齐“让谁在什么场景完成什么任务”和“怎样算有价值”。给一句可套用示例，但不要求固定格式。
- 5W2H 是内部检查骨架，不是问卷：Why、Who、What、When、Where、How、How much。详细维度和角色化人话问法读取 `low-friction-dialogue.md`；每轮只选择一个最影响方向的缺口。
- 可逆、低风险默认可作为 Assumption 直接给出，并写明理由和修改入口；角色、范围、权限、收费、完成/解锁、数据语义和验收口径必须显式确认。

## 2. 需求收拢

至少形成：

- 目标用户、使用场景、核心问题、预期结果；
- In-Scope、Out-of-Scope、MVP/Should/Could；
- 成功指标：基线、目标、观察窗口、数据来源和负责人；缺少基线时标记待验证；
- 已知事实、假设、研究证据、开放问题和阻塞项；
- 一个从触发到结果、反馈/复访和异常兜底的业务闭环。

问题优先问会改变产品方向的内容，不先追问主题色、按钮数量或技术框架。用户只回答一部分时保留已答内容，只追问当前最高影响缺口。

### S2→S3 最小就绪检查

进入规格生成前，内部逐项确认以下五项；这是必要条件，不替代 `lifecycle-orchestration.md` 原有的 S2 退出门槛：

1. **目标用户**：谁执行核心任务，谁只协作或查看；
2. **预期结果**：解决什么问题，出现什么可观察变化才算有价值；
3. **唯一主任务**：用户从什么触发开始，要完成什么结果；
4. **首期边界**：至少有 In-Scope，并明确一个 Out-of-Scope 或延期项；
5. **核心规则**：至少一条会约束主流程、完成口径、权限或异常处理的已确认规则。

五项齐备且主流程、完成规则、高影响缺口满足原门槛，才可标记 `Ready for Specification`。缺项时继续用低摩擦方式只问最影响规格的一项；用户提前索要完整 PRD、功能矩阵、页面、高保真、接口或表结构时，只返回 250 字以内的未就绪说明和一个阻塞问题，不生成占位矩阵或把 Draft 写成已就绪规格。用户只要求对已确认内容做摘要时可正常输出摘要。

“至少一条核心规则”不是对其余高影响规则的豁免。金额/分润/退款、角色权限、完成/解锁、算法数据语义或关键状态转移中，只要某条 Must 的输入、金额、守卫、目标状态或 AC 会随未决规则变化，该 Must 只能标记 Draft/Blocked；不得用“不影响 Must 骨架”绕过 Gate。可交付不受影响的已确认子集，并把受阻项、责任人和确认时机单独列出。

## 3. 产品架构

先识别业务对象，再识别页面。每个核心对象记录业务含义、所有者、生命周期、关联对象、可见范围和业务不变量。

流程步骤至少包含：角色、触发、输入、动作、判断、输出、下一步和失败兜底。区分对象状态与触发状态变化的事件。出现多人、异步、时间、并发、撤回、权限变化、资金/额度、发布生命周期或断网恢复时，自动读取 `state-test-gates.md`。

权限至少拆成：身份认证、角色授权、数据范围、临时授权；说明无权操作、授权到期和撤销后的反馈。跨系统能力记录数据所有者、触发方向、输入输出、失败责任和人工兜底，不伪造 API 字段。

## 4. 功能与验收规格

功能矩阵推荐字段：

| 功能 ID | 目标/任务 | 模块与功能 | 角色 | 优先级 | 依赖 | 规则/状态 | 页面/入口 | 验收标准 |
|---|---|---|---|---|---|---|---|---|

- 优先级用 Must/Should/Could/Won't 或明确的 MVP/P1/P2。
- 用户故事可用“作为……我希望……从而……”，但不能替代规则与 AC。
- AC 优先使用 Given/When/Then，并覆盖权限、异常、空值与数据边界。
- 正式规格或交接中的每个 Must 至少显式带出：目标/任务、角色或 Owner、页面/系统入口、规则/状态、AC 和关联测试；Owner 未知时写 `待确认`，并降低交付状态。
- 输出规格前先将候选项分成互斥的 `Ready 子集` 与 `Blocked 子集`。任一金额口径、Owner/角色、入口、守卫、目标状态或 AC 未决的条目只能进入 Blocked；不得在 Ready 表的一行里一边写功能，一边注明其正向验收尚未确认。未给出的 Owner 保留待确认，不按常识补成财务、管理员或研发。范围优先级与交付就绪度必须拆成两列；高影响规则未决时只能写 `Must 候选 / Blocked`，不能以“首期 Must”“Must 基线”命名表格或结论，也不能为受影响部分给出完整正向 AC。资金业务若缺计算基数/公式/舍入、唯一触发事件、结算时机或退款恢复规则，生成、结算、冻结、冲正等受影响功能必须整体留在 Blocked；不能把粗粒度目标改写为已确认的正向验收。
- 通用登录、首页、设置不自动进入 Must，除非它支撑当前闭环。
- 搜索、通知、推荐、导入导出、金额/积分等能力只有命中需求时展开对应边界。

## 5. 信息架构、页面与组件

IA 说明 1–3 级层级并回指业务目标。每个核心页面至少记录：目标角色、进入条件、唯一主任务、主/次操作、内容优先级、加载/空/错误/成功/无权限状态、响应式和无障碍边界。

空状态区分：尚未创建、筛选无结果、无权限、加载失败、数据暂不可用；每类都有下一步。页面和功能必须双向追溯。

组件按基础样式、基础组件、复合组件、页面模板整理。组件规格至少包含用途、变体轴、进入/退出条件、内容规则、数据/事件、响应式/无障碍和维护责任。表单补充保存中、未保存离开、重复提交、失败恢复；列表补充排序、筛选、分页/虚拟滚动、批量与部分失败。

只有需求结构稳定后才给视觉方向。先确定信息层级、操作层级和状态，再给不超过三个有取舍的风格方向；组件体系名称只作为需求级映射，不代表项目已安装或代码已生成。

## 6. 教育与内容产品附加规则

命中课程、图书、题库、练习或学习进度时读取 `project-functional-playbook.md`，并至少检查：

- 学习者端与内容生产/运营端是否真实存在；未确认角色不生成完整后台。
- 内容类型与动作分开建模；浏览、开始、进行中、完成、收藏和退出未完成不是同一状态。
- 持续学习需要“继续学习”入口、最近有效位置、跨设备/离线边界和内容下线兜底。
- 完成、正确率、解锁、评分、推荐或自动判定都需要来源与口径；未确认时不得静默补全。
- 作答会话、提交、评分、反馈、订正/复习分别建模；主观题不默认自动判分。
- 内容可见与内容可用分别建模；年级、地区、学科、订阅或活动资格不互相替代。

## 7. 边界与压力输入

进入页面/组件规格时按需读取 `a2ui-defensive-ui-contract.md`：P0 缺失不能展示成功态，P1 缺失保留主结构，P2 缺失自动坍缩。至少为适用项定义长文本、全空选填、极值、延迟、失败和无权限的可观察验收；不得把某个 CSS 技巧写成唯一需求方案。
