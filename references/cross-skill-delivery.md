# 跨 Skill 交付编排协议

当用户在需求分析后继续要求高保真原型、研发任务、测试资产、图表或其他专业产物时使用。本协议让当前 Skill 负责交付编排和需求追溯，不把专业实现能力伪装成自身能力。

## 1. 触发条件

出现以下任一请求时启用：

- “进入高保真设计 / 做交互原型 / 生成页面”；
- “拆研发任务 / 给开发交接 / 生成接口任务”；
- “生成测试用例 / 状态机 / 验收清单”；
- “把结果交给另一个 Skill / 工具继续完成”。

只要求 PRD、功能矩阵或页面规格时，不启动跨 Skill 编排。

## 2. 编排边界

- 当前 Skill 仍负责：需求基线、证据标签、决策状态、功能与页面追溯、Ready 门槛和返回审计。
- 下游专业能力负责：原型文件、设计源文件、实现代码、测试脚本、图表或其他专业格式。
- 优先使用用户明确点名且当前可用的 Skill；未点名时按产物类型选择当前环境中最匹配且权限范围合适的能力。
- 不得假设某个 Skill、插件或外部平台一定存在。不可用时交付完整的 Handoff Manifest，并明确“尚未生成目标产物”。
- 调用下游能力不扩大授权。发布、推送、部署、发送消息或写入外部系统仍需用户已明确授权。

## 3. 交付状态

| 状态 | 判定 |
|---|---|
| Needs Decision | 高影响规则缺失，继续会改变角色、范围、主流程或验收口径 |
| Blocked | 目标能力或必要输入不可用，无法安全生成产物 |
| Ready | 需求基线已冻结，低影响假设已标注，允许交给下游能力 |
| In Progress | 下游能力正在生成或验证产物 |
| Completed | 产物已生成并通过返回审计 |
| Failed | 生成或验证失败，已记录失败原因、影响与恢复入口 |

未达到 Ready 时，不得用视觉稿、代码或测试文件掩盖需求缺口。

这些是单次 Delivery 的执行状态；项目全局阶段与交付状态以 `ProjectSnapshot.current_stage` 和 `delivery_status` 为准。创建 Delivery 时必须记录两者，返回审计后再写回，不另建平行项目状态。

## 4. Handoff Manifest

每次跨 Skill 交付先生成一份最小清单；字段可以嵌入回复或交接文档，不要求单独建文件。

| 字段 | 内容要求 |
|---|---|
| Delivery ID | `DEL-001` 形式的稳定编号 |
| 目标产物 | 文件/页面/任务/测试或图表的明确名称 |
| 来源基线 | `project_id`、当前阶段/交付状态、需求版本、适用范围和生成时间 |
| 已确认决策 | 只引用已确认的决策 ID 或原文，不重新解释成新规则 |
| 功能与页面范围 | 功能 ID、页面 ID、角色、主任务和必须状态 |
| 允许假设 | 低影响假设、默认保护动作和替换入口 |
| 禁止推断 | 不得由下游自行决定的业务规则、数据或权限 |
| 视觉/技术约束 | 平台、视口、风格继承、组件体系或实现边界 |
| A2UI Contract（适用时） | `intake_id`、`contract_id`、P0/P1/P2 Slot、已登记 Token、允许 Patch、压力用例与禁止的 L3 推断 |
| 验证要求 | 必跑交互、状态、格式、可访问性和验收检查 |
| 输出位置 | 目标目录或返回形式；不使用未解析的模糊路径 |
| 回传要求 | ART-ID、产物路径、验证结果、失败项、未决项和 DEC/F/P/TR/AC/T 追溯表 |

## 5. 产物路由

| 用户目标 | 交付给下游前必须具备 | 返回后检查 |
|---|---|---|
| v0.3 结构原型 / 低保真流程验证 | 已确认主任务、页面关系、关键状态、锁定/空/完成等规则与目标设备尺寸 | 页面可点击呈现主路径；未确认业务规则未被固化；每个关键状态有明确去向；本地预览与验证记录可复现 |
| v0.4 中保真交互线稿 | Ready for Prototype、真实信息密度、P0/P1/P2、主次操作、Mock 边界与可重复验证任务 | 主路径可操作；守卫拒绝/失败/恢复有出口；页面与 DEC/F/P/TR/AC/T 可追溯；技术、用户和交接证据分开 |
| 高保真页面/交互原型 | 页面目标、页面清单、布局骨架、关键状态、交互规则、视觉继承约束 | 页面与功能双向追溯、主链路可操作、状态可见、无静默补规则 |
| A2UI Studio/受控预览 | Intake/Decision/UI Contract、基线版本、允许 Patch、压力用例 | Patch 可回滚、只修改允许范围、ST-ID 有结果、L3 未被 GUI 静默改变 |
| A2UI Asset Bundle/组件交付 | Bundle Manifest、Contract、质量门槛、外部授权状态 | 产物路径与追溯可打开；本地验证、注册、导出、运行时消费、部署状态不混淆 |
| 研发任务拆分 | 功能矩阵、对象状态、依赖、验收标准、未决项 | 每个 Must 有负责人/依赖/完成定义，Blocked 不混入 Ready |
| 测试用例/状态机 | 对象、事件、状态、守卫条件、超时和异常规则 | 每个关键转移有正向、拒绝或恢复测试，测试能回指决策与功能 |
| 图表/汇报文档 | 权威数据、受众、结论和证据范围 | 图中关系不新增业务事实，标签与正文一致 |

## 6. 执行顺序

1. 识别目标产物和当前需求基线。
2. 检查 Ready；有高影响歧义时只提出 1 个阻塞问题。
3. 从 `ProjectSnapshot` 生成 Handoff Manifest，并把阶段、需求版本和决策状态冻结为本次输入。
4. 选择并使用可用的下游专业能力；结构原型优先选择能生成并验证低保真可点击页面的能力。执行过程中出现新业务规则时退回 Needs Decision。
5. 获取产物后执行返回审计，不把“文件已生成”当作完成。
6. 回写产物路径、验证证据、需求追溯和仍未解决的问题。

## 7. 返回审计

至少检查以下内容：

- 目标范围内每个 Must 功能均有产物入口；
- 产物中的核心操作能回指功能 ID 和已确认决策；
- 未确认规则仍明确标记，没有被样例数据或界面文案固化；
- 加载、空、错误、权限、超时或并发状态按项目风险覆盖；
- 输出文件可打开，必要的脚本、链接或图表可验证；每个文件或可定位产物分配 ART-ID；
- 新增假设、失败项和范围偏差已写回，而不是留在下游工具上下文中。

如果本次是只读审计/评审，结论末尾必须明确写“未修改、发布或推送任何外部产物”。这既是授权边界声明，也让评审记录不会因没有实际写入而产生歧义。

返回摘要使用以下字段：

| Delivery ID | 产物 | 路径/链接 | 验证结果 | 覆盖的功能/决策 | 偏差与未决项 | 状态 |
|---|---|---|---|---|---|---|
