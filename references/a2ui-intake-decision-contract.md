# A2UI 输入与决策协议

用于将一句话、截图、Figma 链接、页面链接或组件描述转换为可编辑的产品 Draft。它是需求控制面的协议，不是代码、渲染器或正式组件注册表。

## 1. 入口与证据边界

| 输入 | 可直接提取 | 必须保留为待确认 |
|---|---|---|
| 一句话/口述 | 目标对象、显式任务、显式结果、语气 | 真实数据、权限、收费、上线承诺 |
| 截图/设计稿 | 可见层级、文案、布局关系、可见状态、视觉线索 | 点击后的业务语义、数据来源、角色权限、隐藏状态 |
| Figma 链接/节点 | 节点、样式、组件层级、可见变量 | 未在节点中表达的规则、服务端能力 |
| 页面链接/现有组件 | 已呈现的入口和交互证据 | 未观察到的对象生命周期与后台规则 |

无法读取或验证的输入必须直接写 `evidence_status: unavailable`，不能基于文件名或用户称呼伪造识别结果。

## 2. IntakeEnvelope

每次首次输入都建立一份轻量记录；用户侧可只显示摘要，完整字段供下游 Handoff 使用。

| 字段 | 含义 | 要求 |
|---|---|---|
| `spec_version` | 协议版本 | 固定为当前版本，如 `a2ui-intake/1` |
| `intake_id` | 本次输入编号 | 稳定、可追溯 |
| `sources` | 输入类型与证据状态 | 每项记录 `text / screenshot / figma / url / component`、可读性和来源 |
| `observed_facts` | 可观察或用户明确陈述的事实 | 每条带来源，禁止推断写入 |
| `draft_target` | 目标角色、场景、页面/卡片候选、终端候选 | 未明确部分标为候选 |
| `confidence` | 事实完整度，不是模型自信 | `high / medium / low` 并说明缺口 |
| `pending_l3` | 会影响业务边界的待确认决策 | 最多展示当前最阻塞的一项 |
| `handoff_route` | 是否需要 A2UI 专项能力 | `none / design-intake / reverse-engineer / runtime-register` |

## 3. DecisionEnvelope 与默认等级

每个默认或用户修改均记录为一条决策；L3 使用 DEC/CHG 账本，不能只留在示例 JSON 或页面文案中。

| 字段 | 含义 |
|---|---|
| `decision_id` | `DEC-*` 或 Draft 编号 |
| `tier` | `L1` 低风险默认、`L2` 可逆候选、`L3` 高影响确认 |
| `status` | `auto-draft / candidate / needs-decision / confirmed / superseded` |
| `value` | 具体采用的值或规则 |
| `rationale` | 默认依据或用户证据 |
| `impact` | 影响页面、组件、数据/规则、验收 |
| `override` | 用户可怎样用自然语言或 Studio Patch 修改 |
| `rollback` | L2 的回退方式；L3 未确认时的保护动作 |

### 等级判定

- L1：间距、内容密度、阅读顺序、默认终端候选、装饰性视觉表达。可以自动进入 Draft，但必须展示理由和修改入口。
- L2：CTA 文案、信息展示顺序、可逆的动效/交互表达。可作为候选展示，必须能通过 Patch 或自然语言回退。
- L3：角色、权限、价格、支付、个人数据、学习完成、解锁、评分、推荐依据、数据口径、上线验收。必须保留为待确认或已有 DEC，不可静默决定。

## 4. 页面字段优先级与防御约束

| 优先级 | 含义 | 缺失策略 | 示例防御规则 |
|---|---|---|---|
| P0 | 缺失即无法表达核心任务/结果 | 不渲染成功态；显示明确空/错误或阻塞反馈 | 标题最长 2 行；主状态图标不压缩；主 CTA 保持可见 |
| P1 | 支持理解或完成任务 | 主结构保持稳定，替换为简短占位或说明 | 描述为空则不留空段；标签超长截断或换行 |
| P2 | 补充信息或装饰 | 自动坍缩，不留无意义间距 | 无积分/徽章/辅助说明时隐藏整个 Slot |

每个 Draft 至少声明：长文本、全空选填字段、极值、加载、失败、无权限六类中的适用规则；未适用时说明原因。

## 5. 面向用户的最小输出

首次回复采用“先给 Draft，再问一个 L3 缺口”的顺序：

1. 一句可理解的项目/页面理解；
2. 3–6 条 `已知事实 / L1 默认 / L2 候选 / L3 待确认` 摘要；
3. P0/P1/P2 与至少一个异常/极端保护规则；
4. 仅一个最影响主流程的 L3 问题；
5. 若输入已足够，附下游 Handoff Route；若不足，写明不能识别的证据而不是假装已读图。

## 6. 与 A2UI 专项能力的边界

本协议产生的是候选输入。实际图稿逆向、Slots/Tokens/IR 编译、Schema 校验、Catalog 匹配、Runtime 注册、受控渲染和发布审计由对应 A2UI 专项 Skill 执行。返回时必须回填 `intake_id`、`decision_id`、功能 ID 与验证证据；若下游新增 L3 规则，退回 Needs Decision。
