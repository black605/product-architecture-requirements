# 生产交接清单

用于把需求分析结果交给设计、开发、测试、运营或业务验收。每一项不满足时，标记阻塞原因和责任人，不用“后续再看”代替。

## Ready：可以进入设计/开发

| 检查项 | 通过标准 | 状态 | 负责人/证据 |
|---|---|---|---|
| 目标 | 一句话说明解决谁的什么问题，以及成功指标 | ☐ | |
| 范围 | In-Scope、Out-of-Scope 和 MVP 边界明确 | ☐ | |
| 角色权限 | 角色、可执行动作和禁止动作清楚 | ☐ | |
| 主流程 | 从触发到结果闭环，步骤和系统响应完整 | ☐ | |
| 异常流程 | 至少覆盖权限不足、空数据、失败重试和关键业务异常 | ☐ | |
| 功能规格 | 功能有优先级、依赖、状态、输入输出和用户故事 | ☐ | |
| 页面承接 | 核心功能有页面或系统入口，页面操作能回指功能 | ☐ | |
| 验收标准 | 使用 Given / When / Then 或可观察结果表达 | ☐ | |
| 待确认项 | 每项有问题、影响、负责人和截止时机 | ☐ | |

## 设计交接包

- 页面清单和 1–3 级 IA 树。
- 每个核心页面的目标、布局骨架、视觉焦点、次要操作和响应式约束。
- 组件映射、变体、加载/空/错误/成功/禁用状态。
- 动效触发、反馈、时长/降级原则和无障碍要求。
- 事实、假设、待验证内容的标记。

## 开发交接包

- 功能矩阵、用户故事、验收标准和依赖关系。
- 业务对象、生命周期状态、权限矩阵和关键规则。
- 需求级数据/接口输入输出，不擅自指定技术框架。
- 非功能要求：性能、兼容性、安全、审计、可观测性和合规。
- 不能由当前需求决定的技术点，列为候选方案和决策人。

## 验收交接包

- 每个 Must 功能至少一个主流程和一个异常验收场景。
- 验收数据、前置条件、预期结果和清理方式。
- 已知限制、降级策略和不在本版本范围内的内容。
- 缺陷严重等级、回归范围和发布门槛。

## Done：可以宣布本轮完成

- 所有 Must 功能均有通过/失败证据。
- 需求、页面、组件和验收标准可以双向追溯。
- 权限、状态、异常和空/加载/错误场景已复核。
- 未决项已转为后续任务，不再阻塞当前交付。
- 版本号、变更原因、影响范围和回归结果已记录。
