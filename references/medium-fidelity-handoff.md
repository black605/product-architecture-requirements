# v0.4 中保真交互线稿交接

在 S4–S5 使用。v0.4 的目标是让真实用户或评审者看懂信息层级、操作优先级、状态变化和恢复路径；它比 v0.3 结构线框更接近真实使用，但仍不是视觉定稿或生产代码。

需要先做低保真页面关系验证时，先读取 `structural-prototype-handoff.md`。

## 1. 启动门槛

- `ProjectSnapshot` 已达到 `Ready for Prototype`；
- 每个 Must 页面已有 `PUI-` 原型 UI Contract，并明确页面骨架、P0/P1/P2、主次操作、组件语义和适用状态；
- 目标用户、主任务、设备/视口、页面入口出口、Must 功能和关键状态明确；
- 会改变页面主操作的完成、解锁、权限、保存/恢复和异常规则已 Confirmed 或明确 Blocked；
- Must 项能追溯到 DEC/F/P/AC/T，缺失组件 ID 不阻塞系统任务；
- 本轮要验证的假设和成功判据明确。

不满足时只交付阻塞表或 v0.3，不用更精细的页面掩盖规则缺口。

## 2. 最小交接包

| 字段 | 要求 |
|---|---|
| Prototype ID | 稳定编号与需求基线版本 |
| UI Contract | PUI-ID、版本、状态，以及 semantic_locked / visual_flexible / pending_decisions / forbidden_assumptions |
| 验证目标 | 要观察的理解、操作或恢复行为 |
| 页面与路径 | P-ID、入口、出口、主/替代路径 |
| 信息层级 | 页面主任务、P0/P1/P2 内容和主次操作 |
| 交互状态 | 正常、加载、空、错误、无权限、进行中、完成及领域状态 |
| 已确认规则 | 引用 DEC/F/TR/AC，不重新解释 |
| Mock/真实边界 | 样例数据、浏览器存储、模拟接口、真实服务分别标记 |
| 允许调整 | 可逆视觉、文案和布局假设 |
| 禁止推断 | 角色、权限、收费、完成/解锁、算法和数据口径 |
| 原型样式 | 默认使用 `prototype-neutral`；标记为 prototype-only，不代表品牌视觉 |
| 验证任务 | 用户任务、独立成功标准、观察项和重置方式 |
| 回传要求 | ART 路径、验证结果、偏差、问题、DEC/CHG 建议 |

## 3. 保真度定义

中保真必须具备：

- 具备接近真实内容长度的真实信息密度，但样例内容有明确标签；
- 可点击主路径及适用的替代/异常出口；
- 页面、组件和状态的稳定层级，主操作不会因选填内容缺失而漂移；
- 清楚的反馈、禁用原因、错误恢复、返回/续学/续办入口；
- 目标设备尺寸下可操作，并具备基础键盘/触控与非颜色状态提示；
- 一键或可重复的测试起点，但测试中不能由主持人替用户执行关键步骤。

中保真不要求：最终品牌插画、生产接口、完整动画、最终 Token、线上埋点或可部署代码。若这些能力尚未接入，必须显示为 Mock、Candidate 或 Pending。

## 4. 状态与压力验证

每个 P0 页面至少验证正常态和与业务最相关的三类风险态；优先从加载、空、失败、无权限、超长、极值、断网/恢复中选择。压力数据是测试输入，不是生产事实。

涉及 Studio 或可视化调参时读取 `a2ui-studio-patch-bridge.md`：只允许受控、可逆、带基线的 Patch；任何 L3 业务变化必须创建 DEC/CHG，不能由 GUI 静默改写。

## 5. 返回审计与版本升级

原型返回后检查：

1. 每个 Must 是否有入口和结果；
2. 页面操作是否回指 DEC/F/P/AC，状态是否回指 TR/T，页面是否回指 PUI；
3. Contract 的 semantic_locked 是否仍被继承，visual_flexible 是否没有被误写成业务规则；
4. 未确认规则是否仍为 Pending，而非被文案、样例或交互定案；
5. 主路径是否可完整操作，守卫拒绝、失败和恢复是否有去向；
6. Mock、本地可运行、真实服务、目标用户测试和生产部署是否被严格区分；
7. 新发现是否已创建缺陷、DEC/CHG 或下一轮验证任务。

达到上述条件可进入 `In Validation`。技术回归通过但真实用户测试未发生时，不得升级 v1.0；按 `prototype-validation-evidence.md` 分别记录技术、目标用户与交接证据。
