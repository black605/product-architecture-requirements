# 项目身份识别闸门

用于每次新对话、资料切换、原型恢复或历史项目复用前，先判断当前输入属于继续旧项目、从旧项目分叉，还是创建新项目。它只决定上下文边界，不代替需求确认。

## 1. 四种决策

| 决策 | 使用条件 | 继承规则 |
|---|---|---|
| `resume` | 用户明确继续同一 `project_id`，核心对象与权威基线一致 | 继承当前 Snapshot，新增 turn delta |
| `fork` | 用户明确以旧项目为起点，但目标用户、主任务、范围或设备形成新产品分支 | 创建新 `project_id`，只复制明确授权的结构证据 |
| `new` | 新产品主题，或旧项目不足以证明同一身份 | 创建独立 Snapshot、UIP 和产物目录 |
| `needs_confirmation` | 同名项目、资料混合、引用指向不清或存在冲突 | 暂停继承，只问一个身份问题 |

不得仅因产品名称、行业、最近一次对话或页面视觉相似就判为 `resume`。

## 2. 判定顺序

1. 检查用户是否明确给出 `project_id`、项目名、已有 Snapshot 或继续/另做/基于旧版等意图。
2. 比较目标用户、唯一主任务、首期范围、核心对象、设备与权威资料来源。
3. 任一高影响身份字段冲突时，优先 `fork` 或 `needs_confirmation`，不能静默覆盖旧项目。
4. 形成 `ProjectIdentityDecision`，再加载对应项目上下文。

结构使用 [`../schemas/project-identity.yaml`](../schemas/project-identity.yaml)。用户侧仍使用自然语言，例如“我会把它作为新项目处理，只参考旧页面的双栏关系，不继承文案和素材”。

## 3. 隔离不变量

- 每个新项目创建新的 `project_id`、`profile_id`、Snapshot 路径和 Harness 运行目录。
- `new` 与 `fork` 默认禁止继承文案、用户数据、视觉资产、品牌 Token、业务规则、权限和算法。
- `fork` 允许继承项必须逐项记录来源、版本、授权与复制方式；共享只读证据不能成为共享可变状态。
- 身份决策改变时，旧决策标记 `superseded`，重新计算 UIP、TFD 和受影响 Contract。
- `needs_confirmation` 时不得读取最近项目原型作为默认模具，也不得生成带旧内容的预览。

## 4. 验收

- 每次进入 S0 或恢复长期项目时都有一个可追溯身份决策；
- 新项目不会继承最近项目内容；
- fork 与 resume 不混用；
- 身份不明时只阻塞继承，不阻塞对用户输入做事实提取；
- ProjectSnapshot、UIP、TFD、PRS 和 Harness run 使用同一 `project_id`。
