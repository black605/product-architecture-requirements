# 产品全周期编排与阶段门槛

用于把一次产品对话持续推进到可验证、可交接、可复盘的交付。主链路是：

```text
输入归集 → 需求收拢 → 产品架构 → 规格生成 → 中保真线稿
→ 方案验证 → 生产交付 → 运营复盘
```

阶段不是文档章节，而是项目状态。每次推进、回改或下游产物返回后，都要更新 `ProjectSnapshot.current_stage`、`delivery_status` 和 `next_gate`。

## 1. 状态词表

只使用以下状态，避免“已完成、基本完成、可用了”等口径漂移：

| 状态 | 含义 |
|---|---|
| Exploring | 输入不足，正在识别目标、用户和问题 |
| Needs Decision | 高影响规则缺失，需要有权角色确认 |
| Ready for Architecture | 需求范围与主闭环已足以建模 |
| Ready for Specification | 对象、流程、状态和 MVP 已稳定 |
| Ready for Prototype | 页面、状态与验收可追溯，允许制作原型 |
| In Validation | 原型或方案正在执行技术/用户/交接验证 |
| Validation Passed | 指定证据层已达到门槛，须注明是哪一层 |
| Handoff Ready | Must 项可设计、开发与测试，交接依赖明确 |
| Blocked | 必要输入、能力或外部依赖不可用 |
| Superseded | 当前基线已被新版本替代，仅保留历史 |

`Validation Passed` 不能单独使用，必须写成“技术验证通过”“目标用户验证通过”或“交接验证通过”；一类证据不能替代另一类。

## 2. 八个阶段与 Ready Gate

| 阶段 | 当前要解决的问题 | 最小产物 | 退出门槛 |
|---|---|---|---|
| S0 输入归集 | 用户给了什么，哪些是事实？ | 输入来源、可观察事实、资料清单 | 产品主题和输入来源已知 |
| S1 需求收拢 | 为谁、在何处、解决什么、结果是什么？ | 项目画像、范围、成功口径、DEC/Pending | 用户、场景、核心任务和预期结果明确 |
| S2 产品架构 | 业务如何闭环，哪些对象与状态承载它？ | 角色、对象、流程、状态、MVP | 目标用户、预期结果、唯一主任务、首期边界、核心规则齐备；In/Out、主流程、完成规则明确；高影响缺口已确认或阻塞 |
| S3 规格生成 | 如何让设计、开发和测试得到同一规则？ | 功能矩阵、IA、页面、AC、测试追溯 | Must 功能、状态、异常、验收均可追溯 |
| S4 中保真线稿 | 用户能否看懂层级并走完任务？ | v0.4 可点击线稿、页面/组件状态、Mock 边界 | 主路径可操作；关键异常有出口；未确认规则未被固化 |
| S5 方案验证 | 技术可运行、用户可理解、交接可执行吗？ | 三类验证记录、问题与优化决策 | 指定证据有记录；失败已进入 DEC/CHG 或缺陷清单 |
| S6 生产交付 | 下游能否无歧义继续工作？ | Handoff Manifest、Asset/任务/测试包、Owner | Must 可开发可测试；依赖、风险、外部授权清楚 |
| S7 运营复盘 | 上线或测试结果如何进入下一轮？ | 指标结论、研究发现、路线图变化、DEC/CHG | 发现已转为继续、调整、停止或补证据的明确动作 |

### 门槛判定

- 高影响问题会改变角色、范围、主流程、完成规则、权限、收费、数据语义或验收口径；未确认时状态必须是 `Needs Decision` 或 `Blocked`。
- 中影响问题可带显式假设推进，但要有 Owner、验证时机和默认保护动作。
- 低影响且可逆的排版、样例内容或视觉默认可进入 Draft，并保留修改入口。
- 不因模板完整、页面可打开或文件已生成而自动升级状态。
- S2→S3 的五项最小就绪字段是必要条件而非降级通道；任一缺失时，即使用户要求完整 PRD，也只输出 250 字以内的未就绪说明和一个阻塞问题，不生成占位 Draft。

## 3. 对话中的最小推进循环

每轮在内部按以下顺序运行；这不是用户可见的五段式模板。S0–S2 的最终回复必须服从 `low-friction-dialogue.md` 的纯文本、250 字和单问题约束：

1. 当前结论：一句话说明项目现在处在哪个阶段。
2. 本轮新增事实：只记录用户新增或材料中可观察到的内容。
3. 决策与变更：创建或更新 DEC/CHG；不覆盖历史。
4. 影响范围：回写目标、对象、功能、流程、页面、组件、AC、测试和产物。
5. 下一步：若门槛未过，只问一个最高价值问题；门槛已过则说明可以进入的下一阶段和产物。

问题优先级使用：`影响程度 × 不确定性 × 不可逆性`。Gate 未通过时每轮只问一个问题；Gate 已通过且用户明确要求比较、清单或交接时才可问两个，严禁超过两个。

## 4. 回退与变更传播

原型、评审、用户测试、研发或指标复盘出现新规则时，不在下游产物中直接修补业务基线：

```text
新证据 → DEC/CHG → 影响分析 → 退回对应阶段 → 更新规格/原型/测试 → 重新过 Gate
```

- 仅改视觉 Token 且不改变业务语义：可停留在 S4/S5。
- 改页面任务、操作优先级或状态反馈：至少退回 S3。
- 改角色、范围、完成/解锁、权限、收费或数据口径：退回 S1/S2，并降低相关交付状态。
- 已交接产物受影响时，CHG 在全部关联产物完成回写前不得标记 `Verified`。

## 5. 版本语义

| 版本 | 语义 |
|---|---|
| v0.1 | 产品需求草案 |
| v0.2 | 产品架构基线 |
| v0.3 | 结构线框，验证页面关系与任务路径 |
| v0.4 | 中保真交互线框，验证层级、状态和恢复 |
| v0.5 | 方案验证候选，已记录三类证据状态 |
| v0.6 | 生产交接候选，Must 项可追溯 |
| v1.0 | 评审通过交付；技术、目标用户与交接证据均满足声明门槛 |

没有真实目标用户证据时，最高只能称“技术验证通过的交接候选”，不得标记 v1.0。
