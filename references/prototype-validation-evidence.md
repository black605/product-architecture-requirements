# 原型验证证据与测试会话规范

当需求已经进入可运行原型、用户测试或交接候选阶段时使用。本规范不规定具体框架、埋点工具或测试平台；只规定可复用的证据边界。

## 1. 三类证据，三个结论

| 证据层 | 要回答的问题 | 最低证据 | 不能证明什么 |
|---|---|---|---|
| 技术行为 | 页面、状态与恢复路径是否按规格运行？ | 可复现操作步骤、自动化或人工回归记录、错误检查 | 目标用户是否看得懂、愿不愿意使用 |
| 目标用户 | 目标人群能否理解、完成并愿意继续核心任务？ | 任务脚本、匿名逐人记录、成功门槛、关键原话/行为 | 接口、模型、权限或跨端同步是否可上线 |
| 交接完整性 | 设计、研发、运营是否知道怎么继续？ | 需求—页面—组件—验收追溯、数据/状态边界、Owner 与未决项 | 真实用户行为或技术稳定性 |

对外结论必须和证据层一致：技术绿灯只能称“技术回归通过”；没有逐人记录时只能称“用户测试计划已准备”；追溯完整只能称“可交接候选”。

项目级候选模具还需单独记录结构审计、跨项目内容隔离、声明设备/状态的技术渲染、目标任务验证、Owner/来源和适用范围。证据不足时不得从 `project-candidate` 升级为共享 `registered`；具体生命周期读取 `prototype-template-lifecycle.md`。

## 2. v0.4 之后的最小验证包

每次原型迭代固定输出：

1. 本轮目标、修改范围和 DEC/CHG 变化；
2. 受影响页面、组件、状态与功能 ID；
3. 技术验证清单：主路径、守卫拒绝、失败恢复、持久化/恢复（如适用）、控制台/页面错误；
4. 目标用户验证计划：任务、目标人群、独立成功口径、观察项、样本与隐私边界；
5. 交接验证：追溯表、Mock/真实能力边界、未决规则与负责人；
6. 未解决问题及下一轮，只将已被证据支持的结论升级状态。

如果某一项尚未执行，写“未执行 / 证据缺失 / 阻塞原因”，不要用完整文档掩盖它。

## 3. 可重复的测试会话

多人顺序测试前，主持人必须定义一个可重复的起始条件：默认账号或匿名会话、初始进度/数据、设备尺寸、网络与权限前提。每位参与者开始前执行一次受控重置，确认其回到相同起点；测试进行中不得重置，也不得由主持人替参与者点击关键决策。

若原型用本地 Mock、浏览器存储或临时数据模拟状态，应提供测试主持人可执行的重置方式，并验证：

- 重置只清理该原型所需的数据，不影响无关用户数据；
- 重置后能回到预先声明的默认任务位置；
- 重置入口只供主持人使用，且执行后不持续污染分享链接或参与者流程；
- 每位参与者的记录使用匿名编号，不收集任务无关的个人信息。

## 4. 目标用户任务记录

每个核心假设至少映射一个可观察任务。记录 `独立完成 / 一次提示后完成 / 未完成`，并保存关键原话或可观察行为。对儿童、医疗、金融或其他敏感人群，先明确同意、监护、最小化记录和数据保留边界；没有适当同意时不收集音视频或可识别信息。

重复风险信号不能被平均值掩盖：若同类误解或放弃行为在两名及以上参与者中出现，应形成独立优化项，关联对应功能 ID、页面/组件、DEC/CHG 和复测任务。

## 5. 结果回写与版本闸门

将每轮结果保存为“逐人记录 + 汇总结论 + 优化决策”。汇总必须分别写出：样本与环境、任务完成数据、重复风险、未解决问题、变更范围、下轮复测项。

- v0.6 可以拥有技术证据、交接材料和待执行的用户测试计划。
- 只有技术回归、目标用户任务门槛和交接追溯三者均满足时，才可标记 v1.0。
- 未达门槛时，按证据更新 DEC/CHG、页面、组件、验收与测试，不得仅用视觉润色替代问题修复。

结果必须写回 `ProjectSnapshot.delivery.validation_results` 和 `evidence.research_findings/pending_validation`。验证发现改变业务基线时创建 DEC/CHG，并按影响退回需求、架构、规格或原型阶段；不只在测试报告中留一条建议。
