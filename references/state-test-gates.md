# 状态机与测试自动触发规则

用于识别“功能列表不足以表达”的动态业务。触发后，先把对象、事件、状态与守卫规则说清楚，再进入页面原型、研发任务或测试交付。

## 1. 自动触发条件

任一核心功能出现以下条件即触发，不等待用户额外要求“画状态机”：

- 两个及以上角色共同改变同一对象；
- 异步处理、消息通知、回调或最终一致性；
- 倒计时、截止时间、有效期、预约或自动失效；
- 取消、撤回、驳回、退款、重交、重试或恢复；
- 并发接受、重复提交、抢占、冲突或幂等要求；
- 登录后仍可能无权限，或授权会过期/撤销；
- 金额、积分、额度、库存、名额或不可超发资源；
- 草稿、审核、发布、下线、归档等生命周期；
- 长任务、断网、后台运行、跨设备恢复；
- 用户明确要求状态机、测试用例或完整异常推演。

只有两个稳定状态且不存在时间、并发、权限或恢复分支时，可以用状态表代替图；仍需保留验收测试。

## 2. 状态建模顺序

1. 识别业务对象，不用页面名称代替对象。
2. 区分“对象当前状态”和“导致变化的事件”。
3. 为每个转移记录发起角色、前置守卫、系统动作、用户反馈和失败出口。
4. 明确终态、可恢复状态、不可逆状态和超时状态。
5. 再把状态映射到页面组件和测试，而不是从按钮反推业务规则。

## 3. 状态转移表

| 转移 ID | 对象 | 当前状态 | 事件 | 发起角色 | 守卫条件 | 下一状态 | 系统副作用 | 用户反馈 | 超时/失败 | 对应决策 |
|---|---|---|---|---|---|---|---|---|---|---|

规则：

- 转移 ID 使用 `TR-对象缩写-001`，测试引用该 ID。
- 每个状态都要说明允许事件；未列出的事件默认拒绝并给出可理解反馈。
- 超时是显式事件，不用“系统自动处理”省略触发时点与结果。
- 并发操作要声明胜出条件、失败方反馈和最终权威状态。
- 重试/回调要说明幂等对象和用户是否会看到重复结果。
- 状态名称使用业务语言；技术队列或数据库字段只能作为候选实现。
- 转移的触发者、触发事件、守卫或唯一目标状态任一未确认时，该转移标记 `Blocked/Pending`，不得写成“Then 进入 A 或 B”之类替代式验收；只对已确认部分派生 AC/T。
- Proposal/Pending 规则不得同时出现在 Ready 转移或 AC 中。交付前逐条扫描 TR/AC：含“暂定、待确认、或、由实现决定”的条目从可开发集合移出，改为 `Blocked TR` 和一个明确待决问题；不得一边标 Proposal，一边为它写可执行验收。
- 目标状态已知但触发方式未定时，可以保留状态名和“未满足守卫不得进入”的负向测试；正向转移不分配 TR/AC ID，也不写“按后续确认规则进入”之类占位验收。确认事件后再创建正式转移与 AC。
- 格式化状态表前先分 `Ready transitions` 与 `Blocked transitions`。Ready 表中每一行必须有已确认事件、发起者、守卫和唯一结果；Blocked 只描述已知起点/目标、缺失决策和影响，不能用箭头伪装为现有转移。两个集合不得出现同一转移。

复杂对象使用 Mermaid `stateDiagram-v2` 表达。图只展示权威状态和关键转移，守卫、失败反馈和副作用仍放在表中。

## 4. 页面状态映射

每个关键页面或组件要区分：

- 业务状态：例如待响应、等待准备、对局中、已结束；
- 请求状态：idle、loading、success、error；
- 权限状态：可见可操作、可见不可操作、不可见、授权失效；
- 数据状态：有数据、尚未创建、筛选无结果、过期、不可用；
- 连接状态：在线、重连中、离线、恢复失败（适用时）。

请求失败不得擅自改变业务状态。UI 上相似的文案也不能合并两个含义不同的业务状态。

## 5. 测试自动派生

每个 Must 转移至少派生：

1. 正向测试：守卫满足，进入目标状态且反馈正确；
2. 拒绝测试：一个关键守卫不满足，状态不变且反馈明确；
3. 恢复或终态测试：超时、失败、取消或退出后能进入定义的状态。

出现对应风险时再增加：

- 并发测试：两个事件同时发生，只有一个权威结果；
- 幂等测试：重复请求/回调不重复产生业务结果；
- 权限测试：无权角色不能执行或读取越权结果；
- 边界时间测试：截止前、截止时、截止后；
- 断网与恢复测试：本地反馈、重连、最终状态一致；
- 跨页面/跨设备测试：离开再进入后显示权威状态；
- 可访问性测试：状态变化有非颜色提示与必要播报。

测试用例字段：

| 测试 ID | 关联决策/功能/转移 | 前置状态 | 操作/事件 | 预期状态 | 预期反馈 | 数据/审计 | 优先级 |
|---|---|---|---|---|---|---|---|

测试 ID 按领域稳定编号，例如 `IN-001`、`TM-001`。测试不能只验证按钮可点击，必须验证业务状态和副作用。

## 6. 三道交付门槛

### 进入原型前

- 所有会改变页面主操作的业务状态已命名；
- Must 转移、守卫和超时规则已确认或明确阻塞；
- 原型需要展示的加载、空、错误、权限和连接状态已列出。

### 进入研发前

- 每个 Must 转移有唯一权威结果和失败反馈；
- Ready 的 TR/AC 不引用 Proposal/Pending；受阻转移与已确认转移分区展示；
- 并发、幂等、超时与恢复规则按触发条件覆盖；
- 决策、功能、转移、页面和验收之间可追溯。

### 进入发布前

- 每个 Must 转移至少有正向、拒绝和恢复/终态证据；
- 所有 P0/P1 缺陷关闭或有明确豁免责任人；
- 未完成测试不会被完整的状态图掩盖。

任一门槛失败时，把对应交付状态标为 Needs Decision 或 Blocked，并指出缺失的决策/转移/测试 ID。
