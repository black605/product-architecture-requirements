# 产品运营闭环与专项工作流路由

在研究、对标、版本规划、阶段汇报或上线后指标复盘时使用。`product-architecture-requirements` 仍是主编排器和单一事实源；`product-management-workflows` 只作为专项分析能力，不另建一套 PRD 或决策状态。

## 1. 路由表

| 触发输入 | 专项工作流 | 写回 ProjectSnapshot | 不得直接做什么 |
|---|---|---|---|
| 访谈、问卷、工单、可用性测试、反馈 | User Research Synthesis | research_findings、置信度、机会点、pending_validation | 少量反馈不能直接升级为 Confirmed 规则 |
| 竞品、市场、定价、行业模式 | Competitive Analysis | 外部事实、定位差异、风险、候选 DEC | 不把竞品功能自动变成本项目需求 |
| 版本规划、优先级、资源与依赖 | Roadmap Management | artifacts/roadmap、Owner、依赖、时间窗、取舍 | 不在容量不变时只加不减 |
| 周报、评审、升级决策、跨团队同步 | Stakeholder Updates | 当前阶段、结论、风险、Decision Ask、下一里程碑 | 不用乐观状态掩盖 Blocked/Needs Decision |
| 灰度、上线、周期经营数据 | Metrics Review | 指标结论、时间窗、数据质量、行动、待验证归因 | 相关性不能写成因果，指标波动不能自动触发改版 |

用户只要求从模糊想法收拢需求、生成架构或 PRD 时，不路由 `product-management-workflows` 的 Feature Spec；由主 Skill 在 S1–S3 直接完成，避免重复访谈和两份权威 PRD。

## 2. 研究证据写回

每条研究发现至少包含：研究问题、来源类型、样本/来源数量、用户分群、观察或原话、频次、影响、置信度、限制和关联的 DEC/F/P。区分“用户说了什么”和“用户实际做了什么”。两名及以上用户出现相同误解或放弃行为时，建立独立优化项并安排复测；样本不足时保留为假设。

对儿童或其他敏感人群，记录监护/同意、最小化采集、匿名编号、保留期限和删除责任；没有适当同意时不收集任务无关的音视频或可识别数据。

## 3. 路线图与沟通写回

路线图项必须关联目标或验证结论，包含状态、Owner、依赖、目标时间窗和“加入它后什么移动或退出”。Roadmap 是结果与取舍视图，不替代研发任务计划。

利益相关方更新从 `ProjectSnapshot` 投影视图：先结论和状态，再写已完成结果、风险、需要的明确决策和下一里程碑。面向管理层讲结果和风险，面向研发讲依赖与 Decision Ask，面向外部用户只讲已验证范围和已授权时间线。

## 4. 指标复盘到下一轮

指标必须记录当前值、对比周期、目标、样本/分母、数据来源、时间窗、分群、数据质量和已知事件。先描述变化，再把原因标为已证实、推测或未知。

复盘输出必须形成一种动作：

- Continue：证据支持继续当前方向；
- Adjust：创建 DEC/CHG，退回受影响阶段并复测；
- Investigate：补充研究、分群或数据质量检查；
- Stop/Defer：明确停止或延后的范围与影响。

```text
研究/指标证据 → 发现 → 机会或风险 → DEC/CHG → 规格/原型/路线图更新 → 新验证
```

没有动作、Owner 和验证时机的复盘不能视为 S7 完成。
