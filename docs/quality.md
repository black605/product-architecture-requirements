# 质量规则与已知缺口

## 发布门槛

任何声称 Skill 修改完成的任务，至少应通过：

1. Skill 结构校验：frontmatter、目录和引用有效；
2. 静态完整性：JSON/YAML、Shell、JavaScript 和 Git diff 检查；
3. 生命周期回归：保持低摩擦对话、需求 Gate、决策追溯和交接边界；
4. 模具与隔离回归：保持 exact/extensible/no_match 和跨项目不污染；
5. Harness 行为回归：Contract、真实浏览器几何、主任务、状态、素材、视觉和有限修复；
6. 变更说明：记录位置、原因、预期防范问题、实际命令和未验证边界。

统一入口：

```bash
./scripts/verify
```

局部验证：

```bash
./scripts/verify structure
./scripts/verify regression
./scripts/verify harness
```

## 证据解释

- 文件存在、关键词命中或 Schema 通过，只能证明协议基础。
- `lint` 通过，只能证明输入 Contract 可编译，不能证明页面可用。
- Harness 通过，证明技术行为和指定任务在当前环境通过，不替代真实目标用户验证。
- 本地预览、Mock 或截图，不等于生产接入、远程发布或部署完成。
- 真实用户验证、外部写入和生产发布必须保留各自证据与授权记录。

## 变更控制

- 单次迭代聚焦一个测试用例或一个核心缺陷。
- 修改后先回跑受影响的上一阶段用例，再扩大验证范围。
- 高影响业务规则、权限、金额、完成/解锁、算法语义和不可逆外部操作必须人工确认。
- 修复 Harness 失败时优先修改对应 Contract 或局部约束；禁止整体重写并掩盖根因。
- 任何新增规则都应能落到可读文件、Schema、脚本或回归测试中。

## 当前已知缺口

- 技术 Harness 通过仍不代表真实目标用户愿意使用。
- 外部 Figma、组件库、目录登记和生产工程消费需要独立连接、授权和返回证据。
- `ProjectSnapshot` 的项目实例文件由使用方持久化；本仓库不会替用户项目自动创建或覆盖状态。
